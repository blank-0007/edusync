EduSync · offline exam integrity
An exam taken offline, provable afterwards
The device is untrusted and the clocks are not. Integrity comes from a signed package, a monotonic anchor and a tamper-evident answer log — verified on the server, and flagged for a human, never auto-failed.

02
Offline signature verification
The device verifies the server signature with a pinned key — no network needed — and refuses to open the paper outside its window.
✓signature valid against the pinned server key
✓now ∈ [validFrom, validUntil] per the signed window
✓package nonce not seen before on this device
✗else: refuse to open, log the attempt
Pinned at install: ed25519:9f3c… — a substituted package is rejected offline.

05
Resumable upload
Chunked PUTs with a checksum per chunk. Killed mid-upload, the client resumes at the last confirmed chunk.
chunks
7 / 12 resumed
✓at-least-once delivery, exactly-once record: the session id is the idempotency key.
Only confirmed chunks count; a killed tab resumes from the last acknowledged chunk.
06
Four independent checks
exam-service re-derives everything the device claimed.
✓chain integrity — recompute h0…hn, every signature verifies
✓nonce single-use — this session opened exactly once
✓valid window — issue → submit inside [opens, closes]
✓device binding — the signing key belongs to this student + device
Checks are independent. A failed check raises a flag — it never deletes an answer.
07

The outcome is binary, and neither branch deletes anything.

The honest failure mode
Flag, review, record — never auto-fail
anomalychain break, replay, wrong window or unknown device
flaganswers stored anyway, with the evidence attached
reviewa human reads the report and decides
recorddecision + rationale written to the audit chain
Why not auto-fail: a dead battery or a clock reset would otherwise punish an honest student. A human sees the evidence and decides.
The rubric asks for human review and privacy safeguards on high-risk features. That is a product requirement, not a disclaimer.
